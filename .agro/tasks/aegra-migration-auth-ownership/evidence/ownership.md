# Data ownership and conditional retirement map

This map inspects repository code on the task branch at `916fb52a`. The map does not count live records or authorize a migration. Each proposed Aegra replacement is a **candidate**, not an equivalent record. Field mappings and retirement tests remain unverified. Do not delete any table, namespace, queue, or object under this task.

## Storage boundary

Orchestra owns `public` in one PostgreSQL database. Its SQLAlchemy sessions, indexed `AsyncPostgresStore`, and checkpoint connections use `backend/src/services/db.py`. `backend/migrations/versions/0000_init.py` creates `users`; `backend/migrations/versions/0001_add_tokens_table.py` creates `tokens`. The latter table holds third-party token slots, **not** the current API-token credentials. Aegra 0.10.7 may own eligible agent state only in the separate `aegra` schema with its own revision and role. The approved pilot is upgrade-only and non-indexed. Orchestra's indexed Store stays in `public`.

The separate Orchestra HTTP service owns credential validation through `GET /api/auth/user` (`backend/src/routes/v0/auth.py`, `backend/src/utils/auth.py`). The proposed Aegra adapter forwards a supplied Bearer token or `x-api-key` to that fixed internal endpoint. The adapter must use the returned persisted user ID. Aegra owns no `public` database connection, public user lookup, or API-token usage update. Orchestra reads `public.users` and updates its own API-token Store entry, including `last_used_at` (`backend/src/repos/user_repo.py`, `backend/src/repos/api_token_repo.py`, `backend/src/utils/auth.py`). The auth adapter and two-user authorization work are separate gates; this map does not claim that they pass.

The opt-in disposable probes described in `.agro/tasks/aegra-migration-auth-ownership/prd.json` exercised an `aegra`-only upgrade, startup precheck, ORM, checkpoint, non-indexed Store, and schema-scoped archive/restore. Those results do not establish a production rollback, Aegra Alembic downgrade, indexed Store safety, or access behavior on unexercised connections. No production restore or live cutover follows from the disposable archive.

## Future decision order

1. **Map and inventory.** If the operator authorizes a later change, enumerate records and references on a safe snapshot. Define explicit field conversions and measure orphaned links. Do not count or modify live records under this task.
2. **Backfill.** If mappings and identity checks pass, copy eligible assistants, threads, runs where recoverable, and checkpoints into `aegra`. Keep Orchestra authoritative. Use one database with separate `public` and `aegra` schema ownership. Do not enable Aegra indexed Store or downgrade.
3. **Prove parity.** If the backfill completes, compare owners, fields, IDs, read results, history, streams, failures, and authorization per surface. Test `GET /api/auth/user` with both credential types through the isolated service. Stop on any Aegra-owned `public` connection.
4. **Switch reads and writes.** If parity and a separately tested reversal plan pass, switch one surface at a time. Preserve the Orchestra source and worker drain controls. Define change capture or a freeze boundary before the switch. This map does not authorize a switch.
5. **Reverse if needed.** If validation fails, restore the prior route and writer only after proving how post-switch changes reach Orchestra. The disposable `aegra`-schema archive/restore does not prove production reversal or recover Orchestra writes.
6. **Delete only after approval.** If post-switch parity, reversal, retention windows, and dependent-consumer tests pass, request a separate operator-approved retirement. Never delete Orchestra users or app-specific data merely because Aegra agent records exist.
